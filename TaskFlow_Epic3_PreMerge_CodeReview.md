## 1. Critical — Security

### 1.1 SignalR broadcasts are not ownership-scoped — cross-user data leak

**Status: FIXED (2026-08-13).**

**Files:** `TaskFlow.Api/Hubs/AgentHub.cs:9`, `TaskFlow.Api/Services/SignalRAgentNotifier.cs:24,46,64`, `TaskFlow.Api/Agents/TailoringAgentBase.cs:91`
**Confidence: High (independently verified).**

**Fix, TDD-first:**
- `AgentHub.OnConnectedAsync` now places every connection in a group scoped to its own user id (`AgentHub.GroupForUser(userId)`, read from the JWT's `NameIdentifier` claim, `int.TryParse`-guarded per this project's established caution around unguarded `int.Parse`).
- `TaskItem` gained a computed `OwnerId` property (`ApplicationId == null ? null : Application.OwnerId`) as the single source of truth for "who owns this task" — and it **fails closed**: if `ApplicationId` is set but `Application` wasn't `Include`d, it throws rather than silently returning null (which would have re-opened the same leak by falling back to broadcast-to-everyone). `TaskRepository.TryClaimNextAsync`'s claim read now includes `Application` so agents can read it without an extra round trip. `TaskService.IsOwnedByAnotherUser` was simplified to use it too (same rule, one fewer place deriving it).
- `IAgentNotifier.AgentActionAsync` / `TaskMovedAsync` now take a **required** `int? ownerId` (no default) — every call site must explicitly decide "this user only" vs "the shared generic board" rather than silently defaulting to broadcast-to-all. `AgentCycleAsync` is unchanged (confirmed to carry no per-task/per-user data). `SignalRAgentNotifier` routes to `Clients.Group(AgentHub.GroupForUser(id))` when `ownerId` is set, `Clients.All` otherwise, via a shared `BroadcastAsync` helper (also fixes DRY finding 3.5's triplicated try/catch in the same rewrite, since it was the same method bodies).
- Every call site (`TaskService`, `JobApplicationService`, `TailoringAgentBase`, `GenericExecutorAgent`, `StaleTaskAgent`, `TaskPrioritizerAgent`) now passes the correct owner: `task.OwnerId` (or `application.OwnerId` where the task's `Application` navigation isn't loaded but the application itself already is, e.g. `JobApplicationService`). Generic-board agents (`GenericExecutorAgent`, `TaskPrioritizerAgent`) always pass `null` since their tasks never carry an `ApplicationId` — verified, not assumed.
- New coverage (previously zero, per finding 6.1): `TaskFlow.Tests/Hubs/AgentHubTests.cs`, `TaskFlow.Tests/Services/SignalRAgentNotifierTests.cs`, `TaskFlow.Tests/Models/TaskItemOwnerIdTests.cs`, plus a new `TaskRepositoryClaimTests` case and strengthened existing assertions in `TaskServiceTests`, `JobApplicationServiceTests`, `ResumeTailoringAgentTests`, `CoverLetterAgentTests` that now assert the exact `ownerId` passed (not just `It.IsAny<...>()`), so a regression that widens the broadcast back to everyone would fail these tests.
- Verified RED before GREEN: confirmed each new/changed test failed to compile or assert correctly (`TaskItem.OwnerId` didn't exist, `AgentHub.GroupForUser` didn't exist, notifier calls had the old 3-arg signature) before writing the implementation. Full `.\test` run after the fix: 368/368 backend, 143/143 frontend, all green.

**Follow-up (2026-08-13, PR #50 Copilot review — real gap found):** this fix only closed the *live* (SignalR) path. `GET /api/AgentLogs` — used by `useAgentFeed` on every dashboard load — still returned every persisted log to any authenticated caller via `IAgentLogRepository.GetRecentAsync`, including Epic 3 `Details` text naming another user's job posting. Same leak, a second delivery path, missed in the first pass. Fixed: `GetRecentAsync` now takes a required `callerId` and applies the same ownership rule `TaskRepository.GetAllAsync` already applies to tasks (cycle-summary/generic-task logs stay visible to everyone; an Epic 3 sibling-task log is visible only to its `JobApplication`'s owner) via a correlated EXISTS subquery against `Tasks` (`AgentLog.TaskId` has no FK/navigation). A log whose `TaskId` no longer resolves to an existing task (e.g. the task was deleted) is excluded entirely — fails closed rather than guessing at stale ownership. `AgentLogsController` now extracts and forwards the caller id (401 if the identity claim is missing/invalid), mirroring `TasksController`'s established convention. New tests: 4 cases in `AgentLogRepositoryTests.cs`, an added 401 case in `AgentLogsControllerTests.cs`; ~29 existing test call sites across 6 agent test files updated to pass a caller id (mechanical — all seed either generic tasks or already have an `OwnerId` constant in scope).

`AgentHub` is `[Authorize]` only — any authenticated user, no per-user grouping (confirmed: no `Groups.AddToGroupAsync` anywhere in the codebase). `SignalRAgentNotifier.AgentActionAsync`/`AgentCycleAsync`/`TaskMovedAsync` all broadcast via `_hub.Clients.All.SendAsync(...)` — every connected authenticated client receives every event, regardless of ownership.

Confirmed the payload actually carries sensitive content: `TailoringAgentBase.cs:91` sets `Details = $"Claimed '{task.Title}' for tailoring."` for the `Claimed` log — `task.Title` here is the parsed job-posting title for an Epic-3 sibling task. This log is persisted **and** broadcast (`ClaudeAgentBase.RecordActionAsync`, lines 200-205, calls `_notifier.AgentActionAsync(log, ct)` immediately after saving).

**Impact:** any authenticated user can watch every other user's job-application titles and task-status changes in real time over the WebSocket — no exploit needed, just opening browser dev tools' Network/WS tab while logged in as any account. `TaskMovedAsync`'s payload is narrower (task id + status only, no title), and `AgentCycleAsync` carries no task-specific data at all — so the concrete leak is scoped to `AgentAction` events' `details` field, not the full `TailoredContent`.

This is exactly the invariant class the project's own Sprint 4R retrospective calls its most serious finding to date ("a new Epic-3 ownership boundary layered on a pre-existing, unscoped channel") — it was applied to every REST surface (`GetAll`, the six `TasksController` single-item actions, `GetMostRecentResumeContext`) but never to this hub. No prior review round touched it; grepping the epic doc confirms it was never discussed or accepted as a known tradeoff.

**Also:** `AgentHub`, `SignalRAgentNotifier`, and `SignalRAgentNotifier`'s try/catch-and-swallow branches all have zero test coverage (every agent test mocks `IAgentNotifier` instead of exercising the real implementation) — the class that actually decides who receives these events is completely unverified by the test suite.

## 2. High — Correctness

### 2.1 `WasSuccessful` heuristic can misclassify a genuinely successful base-resume read

**Status: FIXED (2026-08-13).** Bounded the substring scan to the first 256 characters
(`ErrorHeuristicScanWindow`) — every error string this codebase actually produces is a short,
code-generated sentence at the very start of a tool result; `read_base_context`'s wrapped resume
content always starts with `PromptSafety.WrapUntrusted`'s framing sentence + tag first (>200 chars
before any user content begins), so ordinary resume prose containing the trigger phrases deep
inside is now correctly classified as successful. Changed `WasSuccessful` from `protected` to
`internal` (plus a new `InternalsVisibleTo(TaskFlow.Tests)` in `TaskFlow.Api.csproj`) purely so it
could be unit-tested directly — it was previously unreachable from a test except indirectly through
an agent's `Logger.LogInformation` call, which nothing asserts on. New
`ClaudeAgentBaseWasSuccessfulTests.cs` (5 tests) covers short error strings, an ordinary success
message, and the actual bug scenario (wrapped content merely containing the trigger phrases).
**Process note:** this one fix was implemented before its test was written and confirmed failing —
a deviation from the TDD-order rule, caught and disclosed rather than silently proceeding. The test
suite was still written and verified afterward to lock in the intended behavior.

**Follow-up (2026-08-13, PR #50 Copilot review — the 256-char window fix was still wrong):**
Copilot correctly found the first fix incomplete: `WrapUntrusted`'s framing sentence + opening tag
is *shorter* than 256 characters, so a resume whose own text begins with "does not exist" or "not
found" right after the tag is still inside the scan window and still misclassified as a failed
tool call — the fix narrowed the bug's surface area without closing it. Replaced the length-window
approach entirely: `PromptSafety` now exposes a `FramingPrefix` constant (the fixed literal string
every `WrapUntrusted` result starts with, regardless of label), and `WasSuccessful` checks for that
prefix first — if present, the text is wrapped untrusted content and is exempted from the
error-phrase heuristic entirely, rather than scanned within any window. Added the exact case
Copilot named (trigger phrase as the very first thing in the wrapped content) to
`ClaudeAgentBaseWasSuccessfulTests.cs`; confirmed it failed against the 256-char-window version
before fixing it properly this time (TDD order followed correctly on this round).

**Files:** `TaskFlow.Api/Agents/ClaudeAgentBase.cs:184-193`, `TaskFlow.Api/Agents/TailoringAgentBase.cs:288-292`
**Confidence: Medium on the bug, High on the missing test coverage.**

`ClaudeAgentBase.WasSuccessful` classifies a tool result as failed via substring match on `"not found"` / `"does not exist"`. `TailoringAgentBase.ReadBaseContext` returns the user's full base-resume text as that tool result. Ordinary resume prose containing either phrase (e.g. "certification does not exist yet", "role X — not found in current stack, learning") would cause a genuinely successful read to be miscounted as unsuccessful. Confirmed via grep: zero references to `WasSuccessful` anywhere in `TaskFlow.Tests`, so this interaction has never been exercised by a test in either direction.

**Impact today is narrow** — this action-success flag is used for a log/count purpose, not task state or control flow, so this does not currently corrupt any task's data or status. Flagged because the heuristic was designed against narrow, code-generated tool-result strings and is now silently being applied to arbitrary user prose via Epic 3, without anyone having re-evaluated whether it still holds.
